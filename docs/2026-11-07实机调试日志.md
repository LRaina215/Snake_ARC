# 2026-11-07 实机调试日志

## 今日结论

**ARC→Helix尚未通过无外力辅助的实机验收。** 今天确认了自动调长的适用性不足、送尾曲线与接管边界不同步，以及“前部仍是过渡形态却报完成”的问题。已完成若干控制入口、提示和归形修复，但不能写成实机切换成功。

下一步优先复用现有重力矩回卷的曲线与控制流程：前部继续螺旋推进，尾段按曲线逐步接入。用户提出的“ARC持续送链、前部获得余长后继续缠绕”保留为整体运动目标；先验证能否接入已有回卷流程，不再把“固定前部角度后单独卷尾”当作已实现的方案。

本总结核对已有实机JSONL、代码和专项报告，没有新增实机命令、仿真或测试。

- 实物为18关节，已修复只改关节数而舵机表仍为20项导致的启动错误；实机与手调入口均按18关节处理。
- 用户确认全蛇放直时，J7、J10、J14仍读到约−86°、−90°、−90°，证实原软件零位不适用于当前装配。已根据该直线记录更新软件零位；没有写舵机内部零偏。

详见[18关节零位及尺寸边界](../validation/reports/hardware18_zero_20261107/README.md)。零位修复不能代替新机械尺寸标定，也不能证明重力估计在所有姿态正确。

## 二、用户五项反馈与核对

### 1. 自动调长的ARC半径不随管道选择

**用户观察：**调长后前部到合适搭管位置时容易掉落；怀疑ARC半径不合适。用户认为既要避免过松打滑，也要避免过紧卡住，不应追求越贴合越好。

**代码事实：**模式4仍以60°模板调长；模式5自动调长会捕获入场实测幅值，但随后固定使用，尚未闭环寻找合适的调长半径。Helix中心线半径与螺距仍为配置值94/130 mm。不能把“选到了材料位置”解释为“找到了最佳半径”。

**判断：**管径、轴距和模块外廓影响几何可达性，摩擦、载荷及承载形态也影响能否顺利送链。紧／松之间存在折中的想法合理，但目前没有已验证的“最佳半径公式”。

本次记录入场模型内拟合截面半径约92.37 mm，送尾确认附近约94.68 mm；它们是按旧尺寸重建的蛇身截面，不是管道半径测量。该例未显示很大的模型内半径失配，不能据此认定固定半径就是掉落的唯一原因。

**状态：未解决。**需要把几何匹配和实际送链／承载效果区分评价，不将简单加紧或放松当作答案。

### 2. Ctrl+5由谁决定调多少、何时开始缠绕

**当前是程序自动决定，不是操作者通过J逐次挑选最佳位置。**

程序读取实测角并选取承载ARC，按设定Helix的每圈长度和当前窗口宽度计算前部材料预算，再选目标窗口；需要时自动调长，完成后进入前部起卷。几何预算使用：

\[
L_{\rm turn}=\sqrt{(2\pi R_h)^2+p^2},\qquad
N_{\rm front}=\left\lceil\frac{L_{\rm turn}}{l}\right\rceil-1.
\]

这里的预算只说明理想曲线需要多少材料，不是最佳位姿或承载能力公式。当前代码另有窗口起点范围和离散化规则。

- **模式4：**J/H分别发起头侧增长／缩短的一段任务，适合人工调长。
- **模式5：**J最多推进1秒控制动作；G连续执行自动规划。它们不负责人工指定调长方向与终点。
- **L：**确认操作者看到的实际支撑状态，不是“再送一段长度”。

用户担心“已经不适合继续调长，程序仍在调”有现实依据：当前调长主要依赖角度跟踪来调速，没有证明实际支撑可靠或识别了所有打滑／卡住状态。部分进给逻辑在大误差下仍保留最低推进速度。因此自动化减少了人工介入，却没有等价地补齐物理状态判断。

**状态：操作含义已澄清；自动目标位置与停止依据仍需改进。**

### 3. Ctrl+U后两端不自然下垂，是否快速使能再失能

**用户观察：**有时两侧不是预期的重力下垂状态，可能影响后续方向估计。

**代码事实：**Ctrl+U只使能配置窗口；`prepare_enabled()`最终对所有舵机写入明确的扭矩开关，并读回核对。窗口外关节写0，失能不是把目标角设为0。

失能不保证立即竖直：管道接触、线缆约束、机械摩擦、初始摆动等都可能影响实际形态；这些是待核对原因，不是本次已经测定的故障来源。

**对提议的判断：**按当前位置短暂使能再失能，本身不会提供“自动展直”的动作。若先命令展直再释放，则可能牵动承载区，也需单独验证。不能把一次扭矩脉冲当成重力方向已重置。

**状态：未加入该操作。**后续先区分使能状态错误与真实被动段未摆正，再决定是否需要独立的辅助展直／释放动作；不能仅为了让观察器有结果而假定末端已经竖直。

### 4. 固定前部、逐节卷尾实机失败；前部向内而非向前

**用户实测结论：**在本次工况下，没有外力辅助时前部会打滑，未能完成预期逐段上管；借助外力后，前部仍呈向内弯曲，未成为统一Helix的一部分。这不能外推为所有工况物理不可行，但足以否定“当前方案已经实机完成”。

**已确认的软件问题：**

- 仅有J10、J11两节尾关节使能时，内部整条曲线已推进约0.5 m；从接收边界J10到J11花了约41.5 s控制时间。这里的位移是内部曲线坐标，不是真实送链量。
- L允许确认前部搭稳后，程序永久锁住了尚未成形的前部目标；最后只检查尾部，却报 `complete`。
- 一次“完成”记录的前部相对当时统一Helix参考最大目标差约48.95°；全身重新拟合最佳相位后，最大差仍约39.34°。并非仅显示视角问题。

**对“Ctrl+6随后归位，所以可能没影响”的更正：**按6本身只接入并保持；之后在 `align` 用J/G，才会向统一Helix参考运动。后续归位不能抵消此前已经发生的打滑、支撑丢失或错误接管，也不能作为ARC→Helix成功的证据。

**已修复：**增加 `helix_normalize`，送尾后先统一全身目标再报完成；全身已使能时可再按5选择归形，再J/G推进。仅验证了目标一致性和控制入口，实际同轴贴管仍待验收。详见[归形修复](../validation/reports/helix_normalization_20261107/README.md)。

**状态：首次送尾的实机运动失败仍未关闭。**

### 5. ARC持续送链，并优先复用重力矩最后的回卷代码

**用户的新方向：**持续调整ARC两侧材料分配，前侧获得余长后继续缠绕和推进，尾侧供应材料；避免固定前部后将尾部整段抬起。用户进一步提出优先复用重力矩末段已有的上管代码。

**已核实的复用基础：**现有 `return_seat → return_wind → return_finish → recover` 已包含逐段接管、缩短尾部直线段、前部相位持续推进，以及最后回归完整Helix。`return_wind`确实会更新前部相位，不是把前部目标永久锁定。因此应优先研究接入这套已有流程，减少重新设计一套卷尾控制的必要性。

**仍需确认的接口：**两种起态都可能表现为前部挂管、尾部下垂，但不能因此认定完全等价。重力矩释放后的尾段应已摆向管轴下方；ARC切换时尾段可能位于侧方，前部包绕长度、绕向和相位也可能不同。当前回卷代码还使用配置的保留关节数和直尾长度预算，不能不看实测状态直接照搬这些固定值。

**下一步优先事项：**核对现有前部挂管状态能否直接接入回卷曲线；复用曲线生成、逐段接管与前进相位，只调整必要的初始曲线和参数衔接。检查实际前部推进、尾侧材料减少与依次上管，不把整身滑移或尾部展直误认为有效送链。ARC持续送链的方案尚未开发，不能写成复用已经成功。
